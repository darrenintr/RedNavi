## Address types, never interchangeable

1. VramOffset: byte position in owned VRAM.
2. GpuMc: memory-controller address in the FB aperture: FB_LOCATION_BASE in 16MiB units plus VRAM offset.
3. GpuPte: physical VRAM address used to encode a page-table backing reference: FB_OFFSET in 16MiB units plus VRAM offset. The FB_OFFSET value is not necessarily equal to FB_LOCATION_BASE.
4. GpuVa: virtual address translated by a specific GPU VMID/GFXHUB or MMHUB. It exists only after real page tables and acknowledged TLB invalidation.
5. DmaIova: device-side DMA address for wired host memory, supplied by an actual DMA/IOMMU mapping, never by a CPU pointer.
6. CpuKva: macOS kernel pointer from IOKit; the mapping proves no GPU physical or virtual address.
7. CpuPhysical: physical host RAM, also NOT a substitute for DMA IOVA.
8. BarByte: byte offset in BAR2/BAR5. IP register bases and doorbell slots are DWORD offsets, so multiply by four exactly once.

Illustration only: if FB_LOCATION_BASE=0x8000, FB_OFFSET=0, offset=0x123000, then GpuMc=0x8000123000 and the local PTE backing is 0x123000. The GPU VA, CPU KVA and DMA IOVA are NOT derivable from these values.

The typed C++ implementations in RedNavi/navi33_address_spaces.h intentionally prevent implicit conversion. CPU-visible aperture limits, VRAM limits, address alignment, DMA mapping ownership, VMID and page-table retention all fail closed.

- compat/include/amd/rn_device.h: selected GC11 GFXHUB flavor field.

- tests/host/navi33_address_spaces_test.cpp, tests/host/navi33_m4_asic_test.cpp: boundary, memory, type separation and M4 profile tests, integrated into make test and GCC/Clang sanitizer CI.

## What still blocks actual RX7600 M4 startup

RedNavi's existing rn_mes_start(vaBase, base, ...) assumes a contiguous, specific RX7800XT GTT/VRAM placement and constructs MQD, ring, fence addresses with a single addition. A Navi33 driver must use independent, pinned BOs with explicitly mapped GPU VAs; do not pass FB MC or CPU pointers in place of a GPU VA.

The PSP13.0.7 loader, MMHUB3.0.2 exact register programming, safely retained VRAM/GTT BOs, IOMMU-backed GART, GC11.0.2 MES KIQ and Scheduler runtime mapping, and real GFX ADD_QUEUE are **not yet implemented/verified in this branch**. The separate Linux boot order planner remains a source-backed path contract.

Next steps: refactor native M4 into bounded PSP / GMC / RLC / ME3 KIQ / Scheduler / SET_HW_RESOURCES / KCQ / KGQ / GPU fence operations with exact resource addresses and owner epochs. Independently prove each GPU-origin fence on a recoverable test system before enabling the next stage. The existing 7800XT code must not change behavior.

The new code performs no Navi33 register writes and does not modify VBIOS, EFI or firmware images. Live hardware writes require explicit stage approval and independent recovery.
