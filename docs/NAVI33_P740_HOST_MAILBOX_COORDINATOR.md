# P7.40 — RedNavi host mailbox coordination

An image-wide, statically initialized mutex now wraps known cooperative RedNavi SMU transport operations across service instances. `rn_smu13_send` takes the image mutex and then the existing device mutex for the full response wait, writes and response/result read. The P7.27 execution and legacy timeout recovery take locks in the same order and release in reverse order. No per-instance init/teardown can reset the image mutex. Independent GPUs are conservatively serialized as well. A Kext reload resets the domain; this is not a physical-device lifetime lock.

The host test drives the actual `rn_smu13_send` with three concurrent mock clients, including two independently locked `rn_device` instances, and checks that their simulated transactions never overlap. It also checks timeout and firmware error release. A source regression test checks coordinator coverage and lock ordering at the reviewed call sites. These tests do not exercise IOKit or hardware.

This is **cooperative software serialization, not exclusive hardware mailbox ownership**. Raw BAR5 writes, indirect access paths that bypass this coordinator, other Kexts and firmware do not acquire this lock. Passive readers are not coordinated. An external writer can still race between any operations. There is no demonstrated cross-driver arbitration, revocation, firmware lifecycle guarantee or reset recovery. The P7.27 hardcoded lease remains false; no new command is enabled. A safely deployable device-keyed coordinator and any cross-driver arbitration still need independently reviewed ownership and teardown semantics. No Kext has been deployed or loaded by this work.
