# RX 7600 P7.16/P7.17: MEC P2/P3 staged PSP loading

This branch extends the real-silicon, guarded P7.15 firmware loading checkpoint. **It does not start GC, RLC, MES, a graphics queue, a framebuffer, or Metal/WindowServer.** On Navi33 (GC11.0.2), the selected Linux gfx_v11_0 RS64 initialization path requests MEC code plus P0, P1, P2 and P3 stack records. P4–P7 are defined by firmware interfaces but are not automatically mandatory on this specific initialization branch.

* P7 step 18, Kext 0.0.36: `rednavi_navi33_p716_mec_p2=1`; PSP `LOAD_IP_FW` command 6, type **96**, current-boot prior fence 14, expected fence 15.
* P7 step 19, Kext 0.0.36: `rednavi_navi33_p717_mec_p3=1`; PSP `LOAD_IP_FW` command 6, type **97**, current-boot prior fence 15, expected fence 16.
* Both reuse the already pinned `gc_11_0_2_mec.bin` GFX v2.0 MEC **Data** region, 139264 bytes, and the existing validated 270336-byte 66-page DMA stage. The firmware is locally generated; no blob is redistributed.

## Deployment safety

These operations write to GPU hardware at boot and can hang the only GPU. Keep the previously validated **0.0.34 EFI** on an independent bootable USB. Do not overwrite your sole recovery EFI. The new stages are opt-in and are not activated by merely setting `rednavi_navi33_p7_step`.

1. Preserve every verified previous P7 boot-arg, including the P7.15 opt-in. Install the new kext only after both host tests and the macOS syntax/build checks have passed. First perform an **admission-only boot** with `rednavi_navi33_p7_step=18`, but **without** `rednavi_navi33_p716_mec_p2=1`. Verify IORegistry `navi33-p7-gc-mec-p2-runtime` has `gate_error=2`, `explicit_opt_in=0`, `submitted=0`, and P7.15 remains accepted at fence 14.
2. Power off, then boot fresh with `rednavi_navi33_p716_mec_p2=1` added. Only proceed if `fence_expected=15`, `fence_observed=15`, `response_valid=1`, `status=0`, `accepted=1`, `transport_error=0`, `transport_quarantined=0`, and `submit_rptr_final=240`.
3. Only after the P2 checkpoint has succeeded, perform an admission-only fresh boot with `rednavi_navi33_p7_step=19`, but **without** `rednavi_navi33_p717_mec_p3=1`. Verify `gate_error=2`, `submitted=0`, and P2 success at fence 15.
4. Power off and boot fresh with both opt-ins. Expect `fence_expected=16`, `fence_observed=16`, `response_valid=1`, `status=0`, `accepted=1`, `transport_error=0`, `transport_quarantined=0`, `submit_rptr_final=256`.

Never resubmit a timed-out/quarantined PSP command during the same boot. Reboot into the known-good EFI for recovery. The derived ring pointers 240 and 256 assume uninterrupted 16-byte per-command progression from the observed P7.15 RPTR 224; treat differences as evidence to investigate, not a reason to force success.

## Check status

```sh
kmutil showloaded | grep -i Navi33
ioreg -r -l -w0 -c RedNaviProbe | grep -E '"navi33-p7-(gc-mec-p[123]-runtime|postpsp-runtime|render-pipeline)"'
```

The current `post_gate_error=12` is `IpFirmwareIncomplete`, not a PSP ring fence failure. The post-PSP gate must continue to reject MES until the remainder of RLC/IMU/SMU, GC/SDMA, and MES Scheduler/KIQ dependencies are verified. Do not set `gcFirmwareLoaded` or `may_start_mes` simply on P3 acceptance.

**Graphics milestone proof** must later include a real GC scratch-register ring test, writeback/IB fence, and verified offscreen GPU output. WindowServer GPU participation requires a functioning framebuffer/DCN and an acceleration/Metal compositor path; a PSP fence alone is insufficient.
